## Context

Sophon users should get Marketplace agents that work the way Claude Code does:
1. research;
2. plan in a markdown file that the user approves, then execute it task by task with a live todo list;
3. implement with TDD;
4. verify with real commands;
5. review adversarially;
6. use git: a feature branch, one commit per verified task, and a PR offered at the end.

They also:
- ask before using sub-agents;
- run "Ultracode"-style multi-agent waves when the user opts in;
- report honestly, with evidence.

The six v1.0.0 personas in `agents/` are ignored and rewritten from scratch. They are built on Sophon's built-in tools (`sophon/src/Sophon.Skills/Tools`), not on this repo's integration skills.

## Runtime facts that bind the design (verified in source)

- **Package contents** (`Sophon.Core/Agents/Packaging/AgentPackageFormat.cs`).
  - Allowed root files: `manifest.json`, `SOUL.md`, `VOICE.md`, `HEARTBEAT.md`, `TOOLS.md`, `README.md`, `LICENSE`.
  - Limits: 64 KiB per file, 512 KiB in all, 16 entries.
  - SOUL.md is used verbatim as the system prompt. It cannot include other files, so shared text is **composed at build time**.
- **Tool pins.**
  - `TOOLS.md` frontmatter `pins:` and per-profile `pins:` are a package's only way to add tool visibility (`Sophon.Core/Skills/ToolSelection/AgentToolPins.cs`).
  - Packages cannot set auto-approve, model pins, delegation allow-lists or effort.
  - `defaults.subAgents {enabled, maxDepth}` **is** applied, on first install only.
- **Coding core** (bound workspace, always loaded): `agent.delegate`, `code.git`, `datetime.now`, `fs.edit`, `fs.find`, `fs.list`, `fs.multi_edit`, `fs.read`, `fs.search`, `fs.write`, `info.request`, `memory.search`, `memory.write`, `os.execute`, `plan.propose`, `plan.recover`, `sessions.yield`, `todo.write`, `web.search`, plus `tools.search` and `tools.load` (`ToolProfile.cs`).
  - The OpenAI family gets `fs.apply_patch` instead of the edit tools.
  - `coding.subagent` drops `info.request`, `plan.propose` and `plan.recover`.
  - Everything else is deferred: called by exact name, or loaded through `tools.search`/`tools.load`, 30 per session.
- **Claude Code analogues.**

  | Claude Code | Sophon | Notes |
  |---|---|---|
  | ExitPlanMode | `plan.propose` | Plan mode is set by the user only. A card of ≤4 linear steps recommends Inline. The Personal-edition Dashboard cannot approve plans. |
  | TodoWrite | `todo.write` | |
  | AskUserQuestion | `info.request` | 1–4 questions of 2–4 options. Blocks for 15 minutes. Refused in children, heartbeat and cron. |
  | Task | `agent.delegate` | `task` or `tasks[2-5]` in parallel. Blocking, depth ≤ min(3, maxDepth), no background mode, no ad-hoc system prompt. Always pass `maxIterations`. |
  | gitStatus | "Git state" block | |
  | CLAUDE.md | AGENTS.md / CLAUDE.md | |

- **Not available, so the personas work around it:**
  - an Ultracode/Workflow tool (Sophon Workflows are owner-run DAGs with no tool-using agent nodes);
  - background shells;
  - push, PR, add, amend, reset or rebase in `code.git`;
  - `web.fetch` (use `web.scrape` readability instead);
  - hooks, worktrees, and resuming after `sessions.yield`.
- **Git.** `code.git commit` stages everything, runs no hooks and adds no trailer. Selective commits, push and `gh pr create` go through `os.execute`, which is Critical: always a card; tokens are stripped from its environment.
- **Approvals.** Marketplace installs are third-party for life.
  - Every Medium-or-higher call raises a card: edits, `os.execute`, `code.git diff` and writes, `agent.delegate`.
  - Inside a child, that holds even with auto-approve on.
  - A medium 4-task plan costs about 28 cards. The README says so and points to the local-install form.
- **Build and test.** `code.test` and `code.build` cannot see the project under the Docker sandbox, so the personas run project commands through `os.execute` (bound shell: 120 s by default, 1800 s at most; cmd or PowerShell 5.1 on Windows).

## Approach

**One family, one shared source.**
- Each `agents/<id>/SOUL.md` is **generated**: an agent template (its role text) plus up to 21 shared **fragments** for the cross-cutting protocols:
  - delegated mode, tools, approvals;
  - sizing, plan format, plan execution;
  - evidence, git, data hygiene;
  - the STATUS and FINDINGS blocks, reporting.
- A PowerShell composer builds the SOULs deterministically, and `-Check` fails CI on drift.
- A lint checks every tool name against a catalogue of real Sophon tools.
- A preflight replays the marketplace's injection and secret scanners before upload, so the packages pass review cleanly.

**Behaviour summary.**
- **Lead Developer** sizes every request:
  - Trivial: done inline.
  - Medium or Large: plan file, approval (with the Agents question when sub-agents would help), branch, then the execution loop.
- **Ultracode-lite.** With consent, the lead runs phase waves through `agent.delegate`: Understand, Design (judge panel), Implement, Review lenses, 3-vote Refute, Fix, Re-review until dry, then a Completeness critic. The plan's `## Orchestration` table acts as the "workflow script", with binding caps.
- **Specialists** use the same sizing, plan and git protocol when the user talks to them directly. The writers are developer, QA, debugger and UX.
- **Read-only roles never commit:** researcher, architect, code-reviewer, security-reviewer. The architect saves only a plan or ADR file, after the user approves it.

**Delegation depth.**
- The other eight are `{enabled:false, maxDepth:0}`. Only the *caller's* policy is checked (`SubAgentOrchestrator.cs:49-62`), so the lead can still delegate to them.
- Why depth 1: consent and card estimates exist only at the root, where `info.request` works.
- Upgraders keep their old `maxDepth 2`, because updates never change `subAgents`. The docs tell them to set it to 1, and fragment 01 forbids delegating while delegated.

**Consent detection** (the user's messages, newest first; the first match wins):
1. "ultracode off" or "no ultracode" → back to asking.
2. "no subagents", "no sub-agents", "without subagents" or "don't use agents" → standing no.
3. "ultracode" → standing yes.
4. "use agents" after a standing no → back to asking.

What follows from it:
- The keyword decides consent only; size still decides the phases.
- A standing yes still requires plan approval, plus a one-line announcement before the first wave: agents, waves, cards, cost.
- Otherwise the lead asks once per task (header "Agents"), only when delegation clearly helps. Solo is always offered.
- No answer or `(skipped)` means Solo. The answer is recorded on the plan's `Consent:` line.

**Wording rules (checked by preflight):**
- No injection literals.
- No `<word>pass:` patterns, which read as possible_secret.
- No "skip/bypass/disable" near approval words.
- No secret word near send/post/upload.
- No `<!--`.
- Never write "auto-approve" in a SOUL.

### Exact strings that must not drift

**Sizing (07):**
- **Trivial:** ≤2 files, ≤40 lines, one obvious approach; no public interface, schema, dependency, build, CI, auth, crypto or permission change → done directly, no plan.
- **Medium:** 3–10 files, 41–400 lines, 2–6 tasks, or one real design choice → plan file, approval, branch, one commit per task.
- **Large:** more than 10 files, more than 400 lines, more than 6 tasks, several modules, a migration, auth or crypto, concurrency, or 3 or more unknown areas → as Medium, plus the lead's phases. Over 20 tasks → milestone plans.
- Never size downward.

**Plan template (08a, verbatim):**
```
# Plan: <title>
Status: draft
Date: YYYY-MM-DD · Agent: <role id> · Size: medium | large · Base: <branch>@<sha> · Branch: sophon/<slug>
Approved: pending | <date> via plan.propose | <date> via info.request | <date> via chat (plan card GO)
Consent: solo | <option> (<date>) | ultracode (standing) | no sub-agents (standing) | no answer → solo
Execution: inline | graph
Request: "<the user's words, verbatim>"

## Goal
## Context
## Approach
## Out of scope
## Verification
## Orchestration
## Tasks
### Task 1: <imperative title>
- [ ] Done
Files: `path` (create | modify | delete), …
Depends on: none | Task N
- [ ] <one action with a checkable result>
Run: `<exact command>`
Expected: <exact result>
Commit: <type(scope): subject>
## Risks
## Progress
```
- The Status vocabulary is `draft | approved | in-progress | blocked | done | cancelled`.
- Tasks are matched to commits by subject, never by sha.
- Forbidden step text: "TBD", "handle edge cases", "add validation", "write tests for the above".

**Approval:**
- **Plan mode on (bound):** `plan.propose` as the last call of its batch, with ≤4 linear steps (`p1-setup` … `p4-finish`) so the card recommends Inline. The summary's first three lines name the plan path, say "choose Inline", and give the **GO escape** for the Personal-edition Dashboard: "Choose Keep planning and type GO".
- **Plan mode off:**
  1. Write the file with `fs.write create_new`.
  2. Ask one `info.request` (header "Plan"): [Approve and start (Recommended)] [Change something] [Cancel], plus the Agents question.
  3. No answer → do not start.

**Execution loop, per task:**
1. Re-read the task block from the file.
2. Do the work, red run first.
3. Make **one plan edit**: tick the boxes, add the Progress line.
4. Run **one verify-and-commit command**.
   - Exit 0 → mark the todo completed.
   - Otherwise, repair at most 3 times, then BLOCKED plus a question.
   - Never commit unverified work.

**Resume:**
- Find the newest plan in progress and reconcile it with the git log. A task is done only when it is ticked **and** its commit subject is in the log.
- Rebuild the todo list and continue. Never redo a committed task.

**Verify-and-commit (Windows cmd, the preferred form):**
```
<run> && git add -A -- "a.cs" "docs/plans/x.md" && git commit -m "feat(api): subject" -m "why" -m "Co-Authored-By: Sophon <noreply@buildersoft.io>" -- "a.cs" "docs/plans/x.md" && git log -1 --stat
```
- PowerShell 5.1 and bash variants are in design §5.2.
- The trailing pathspec keeps files the user staged out of the commit.
- A long or non-ASCII message goes through `fs.write sophon-scratch-commit.txt`, then `git commit -F`.
- Never, unless the user asks for that exact operation: amend, rebase, reset, clean, force-push, push to the default branch, change git config.

**End-of-task menu:** `info.request`, header "Git".
- Options: [Push + open PR (Recommended)] "2 approvals" · [Keep local] · [Discard] "after one more confirmation".
- Keep local becomes the recommended option when something is unverified, there is no remote, or the remote isn't GitHub. A non-GitHub remote turns option 1 into "Push branch".
- No answer → Keep local.
- **Push + PR:**
  1. `fs.write sophon-scratch-pr.md` (Summary / Changes / Test plan / Plan path, then a blank line and the footer as the last line).
  2. `git push -u origin sophon/<slug> && gh pr create --base <base> --head sophon/<slug> --title "…" --body-file sophon-scratch-pr.md && del sophon-scratch-pr.md`.
- **Auth failure:** quote the error and tell the user to run `gh auth login`, `gh auth status` or `gh auth setup-git` themselves. Never ask for a token.

## Ultracode-lite (lead role text)

The plan's `## Orchestration` section holds:
- a Consent line and an Estimate line (agents, waves, cards, ≈k× Solo tokens);
- a Companions line, found once per task with `agent.list`, matching the `Family role: <slug>.` marker in whenToUse;
- a wave table.

| Phase | When | Shape | Child budget (maxIterations) | Gate |
|---|---|---|---|---|
| Understand | Large; Medium with more than 15 files to survey, or web plus code | one `tasks[]` call, 2–5 researchers, each with a distinct focus, read-only tools | 25 | ≤400 words each, every claim path:line or URL; the lead opens the key lines itself |
| Design (judge panel) | Large | 2–3 architects, minimal / clean / pragmatic | 20 | a rubric written first (14 points), winner plus grafts → Ruling; tied and user-visible → ask |
| Implement | Large, or Medium with a heavy context | serial: one developer per task; parallel: ≤3, only with disjoint files and no builds or tests in the child | 40 | the lead runs verify-and-commit itself |
| Review | every Medium or Large task with consent | one review-diff scratch file (1 card); 3 lenses (Medium) or 4–5 (Large, + security-reviewer / UX / QA where relevant) | 25 | FINDINGS at confidence ≥ 80 |
| Refute | every Critical and Important finding | 3 code-reviewers in `refute` mode, lenses reachability / impact / defences (security findings go to security-reviewer `verify` ×3) | 15 | ≥2 of 3 CONFIRMED; a missing vote counts as REFUTED |
| Fix → Re-review | confirmed findings | a test that fails then passes; `fix(...)` commit; re-review until dry, ≤3 rounds | 40 / 15 | caps are logged |
| Critic | Large; Medium with 4 or more tasks | one code-reviewer in `completeness` mode | 15 | the lead checks each item |
| Bug hunt | "find bugs" or "audit" | 1–3 rounds of 3–5 finders, deduped against KNOWN, then refuted | 25 | dry = a round finds 0 new confirmed |

**Brief template** (the `task` text): `ROLE · MODE · ACCESS / GOAL / WHY / CONTEXT / READ_FIRST / WRITE_SCOPE / RULED_OUT / CONSTRAINTS / ACCEPTANCE / BUDGET / <role keys> / END WITH`, at most 6,000 characters.

**Children:**
- start blank;
- never commit, never ask the user, never delegate;
- end with the STATUS block: `STATUS: DONE|DONE_WITH_CONCERNS|BLOCKED|NEEDS_CONTEXT`, `VERDICT`, `SUMMARY`, `FILES_CHANGED`, `COMMANDS_RUN`, `EVIDENCE`, `ASSUMPTIONS`, `OPEN_QUESTIONS`.

**Caps:**
- Medium: 10 agents and 5 delegate calls. Large: 25 agents and 14 calls.
- At most 5 entries per call. Always pass `maxIterations`; never pass `model`.
- The estimate is binding: anything dropped is logged as `Cap:`, and the lead never asks twice.
- A missing companion gets a stand-in (≤2 per wave) with a pasted checklist, labelled lower confidence.
- **Don't fan out when:**
  - the work is ≤8 tool calls;
  - the edits are coupled;
  - the diagnosis is sequential;
  - consent is no;
  - in doubt.
- In plan mode only Understand and Design run.
